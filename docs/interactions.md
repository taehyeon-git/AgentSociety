# 협상·공동 생산·목표 적응

엔진 0.5.0은 상대를 지정하는 가격 협상, 두 에이전트의 공동 생산, 실제 성과에 따른 주기적 목표 변경을 지원합니다. 세 기능은 독립적으로 설정하며 기본값은 모두 꺼짐입니다. 기존 경제 실험과 비교할 때 같은 초기 시드를 사용할 수 있습니다.

```sh
cargo run --release -p agentsociety-cli -- --config examples/phase5.json --ticks 1000 --summary-out runs/phase5-summary.json
cargo run --release -p agentsociety-desktop -- --config examples/phase5.json
```

예시 설정은 100명·시드 42이며 협상과 공동 생산을 켜고 50 Tick마다 목표를 검토합니다.

```json
{
  "interactions": {
    "negotiation": true,
    "cooperation": true,
    "offer_lifetime_ticks": 4,
    "goal_review_interval": 50
  }
}
```

제안 수명은 1~64 Tick, 목표 검토 간격은 0~1,000,000 Tick입니다. 간격 0은 목표 적응을 끕니다. GUI의 `Social behavior (apply with Restart)`에서도 두 기능과 검토 간격을 바꿀 수 있으며 `Restart`로 새 실행에 적용합니다. 진행 중인 실행의 계약 조건을 바꾸지는 않습니다.

## 가격 협상

`Negotiate`는 상대, 매수/매도 방향, 자원, 수량, 단가를 지정합니다. `side`는 현재 제안자 관점입니다. 한 번의 수락으로 전체 수량을 거래하며 부분 체결은 없습니다. 일반 중앙 주문장과 병행합니다.

```json
{"action":"negotiate","counterparty":2,"side":"buy","resource":"wood","quantity":2,"unit_price":70}
```

| 행동 | 권한과 결과 |
| --- | --- |
| `Negotiate` | 제안자가 현금 또는 판매 재고를 예약하고 상대에게 제안 |
| `CounterOffer` | 수신자가 수량·가격을 변경; 기존 예약 해제와 새 제안자의 예약을 함께 확정 |
| `AcceptProposal` | 수신자가 자신의 자산을 제공하고 두 계좌의 화폐·재고를 원자적으로 교환 |
| `RejectProposal` | 수신자가 거절하고 제안자의 예약 해제 |
| `CancelProposal` | 현재 제안자가 철회하고 자신의 예약 해제 |
| 만료 | 응답 없이 기한이 지나면 예약 해제, 거래 없음 |

응답은 `{"action":"accept_proposal","proposal_id":0}` 형식입니다. 역제안은 `{"action":"counter_offer","proposal_id":0,"quantity":2,"unit_price":80}`입니다. 역제안 때 제안자·수신자·매수/매도 방향이 뒤집히며, 자원과 ID와 최초 만료 시점은 유지합니다.

에이전트별 진행 중 제안은 들어온 것과 보낸 것을 합쳐 최대 4개, 같은 두 에이전트 사이에는 종류를 합쳐 최대 1개입니다. 역제안은 최대 3회입니다. 매 Tick 한 개의 주 행동만 선택하므로 제안과 응답도 행동 기회를 사용합니다. 자기 자신이나 없는 상대에게 제안할 수 없습니다.

Tick 1에 수명 4로 만든 제안의 기한은 Tick 5입니다. Tick 2~5에 응답할 수 있고 Tick 6의 행동 적용 전에 만료됩니다. 방금 생성하거나 수정된 제안은 같은 Tick에 응답할 수 없습니다. 제3자 응답, 기한이 지난 응답, 잘못된 역할, 자금·재고 부족을 거절합니다. 검증 실패 시 두 계좌와 제안은 그대로 유지됩니다.

일반 주문 예약은 매 Tick 해제되지만 제안의 예약은 계약 종료까지 유지됩니다. 사용 가능한 자산에서 제외하고 총 자산에는 정확히 한 번 포함합니다. 다음 Tick을 결정할 때 규칙 정책과 LLM은 같은 완료 상태를 보며, 해당 Tick에 만료될 제안은 관찰에서 제외합니다. 만료 자산의 해제는 결정 수집 후 행동 적용 전에 수행합니다.

수락한 거래만 `NegotiatedTrade`와 거래 기억을 만듭니다. `trade_count`·거래 대금·수량에 포함하고 `negotiated_trades`로 별도 집계합니다. 가격은 중앙 체결과 협상 체결을 합친 수량 가중 평균의 정수 내림입니다. 제안·역제안·거절은 가격이나 실제 거래량을 바꾸지 않습니다. 매수 수요·매도 공급 지표는 중앙 주문장에 제출한 수량을 계속 의미합니다.

## 공동 생산

현재 협력은 **두 명의 공동 제조 계약**입니다. Producer가 `{"action":"cooperate","partner":3,"producer_share":2}`로 시작합니다.

1. 제안 시 Producer의 Metal 2개를 예약하고 준비 에너지 5를 즉시 사용합니다.
2. 상대가 수락하면 사용 가능한 Wood 4개와 에너지 5를 제공합니다.
3. 두 재료를 소비하고 Goods 4개를 생산합니다. Producer 몫은 1~3개, 상대 몫은 나머지입니다.
4. 입력·출력·에너지 검사를 모두 마친 뒤 두 계좌를 함께 확정합니다. 현금은 이동하지 않습니다.

고정된 공동 작업 레시피이며 개인 제조의 기술별 생산량과 별개입니다. 거절·취소·만료되면 Metal 예약은 해제되지만 이미 사용한 준비 에너지는 반환하지 않습니다. 수락 실패 시 상대의 재료·에너지를 소비하지 않고 기존 제안을 유지합니다. 공동 생산의 역제안은 지원하지 않습니다.

실제 원재료 소비는 `ResourceConsumed(ProductionInput)`, 결과물은 두 개의 `ResourceProduced`로 기록합니다. `CooperationCompleted`는 협력 완료 횟수·관계·기억의 근거이며 생산량을 중복 집계하지 않습니다. 다자 조직, 공유 재산, 지도자 선출, 장기 고용 계약은 아직 없습니다.

## 관계와 상대 선택

협상 체결은 양쪽 신뢰 +3, 공동 생산 완료는 양쪽 신뢰 +5·협력 점수 +10입니다. 완료 사실 한 번당 친밀도 +2와 상호작용 수 +1을 기록합니다. 거절·만료는 제안자의 상대방 신뢰 -1, 철회는 수신자의 제안자 신뢰 -1입니다. 단순한 중앙 미체결 주문에는 상대를 특정한 실패 관계를 만들지 않습니다.

관찰에는 본인의 응답 가능한 제안 최대 4개와 상대의 공개 요약 최대 8개를 제공합니다. 상대는 주요 관계와 순환하는 안정적인 ID 순서로 고르며, 전체 기억이나 전체 계좌를 노출하지 않습니다. 공개 요약은 직업, 사용 가능한 재고·현금, 에너지, 식량 목표량, 진행 중 제안 수입니다. ID 순회는 공간적 거리를 의미하지 않습니다.

규칙 정책은 식량 위기를 먼저 처리하고 들어온 제안을 검토합니다. 실제 필요량·지불 한도·보유량을 만족하는 가격은 수락하고, 가능하면 역제안합니다. 새 상대는 음의 신뢰를 피하고 높은 신뢰와 낮은 ID를 우선합니다. 매 8 Tick의 ID별 기회에 구매/판매를 협상으로 제안하며, 준비된 Producer는 매 12 Tick의 기회에 공동 생산을 제안할 수 있습니다. 새 제안을 이미 갖고 있으면 응답과 경제 행동에 집중합니다.

## 목표 적응

`GoalProgress`는 최근 검토 이후의 기아 Tick, 거절된 행동, 실제 거래, 완료 협력과 기준 자산을 보관합니다. 기억 보관량을 0으로 설정해도 이 성과 기록은 유지됩니다. 이는 학습된 정책이나 강화학습이 아니라 명시적인 적응 규칙입니다.

설정 간격마다 자동 소비가 끝난 상태에서 다음 우선순위로 검토합니다.

1. 사용 가능한 Food가 2 이하, 기아가 40 이상, 또는 검토 구간의 25% 이상에서 기아가 발생했으면 `SecureFood`.
2. 현재 `SecureFood`이고 Food가 14 미만이면 목표를 유지하여 잦은 왕복 변경을 억제.
3. 이전 검토보다 기준 자산이 15% 초과 감소했으면 `BuildWealth`.
4. Merchant가 구간 내 실제 거래를 2회 이상 마쳤으면 `TradeProfit`.
5. Food가 10 이상이며, 쾌적도가 50 미만이거나 구간 내 협력을 완료했으면 `StableLife`.
6. 회복된 `SecureFood`는 `BuildWealth`로 전환하고, 나머지는 기존 목표 유지.

기준 자산은 항상 **초기 가격**으로 평가하여 시세 상승만으로 성과가 좋아진 것으로 판단하지 않습니다. 변경 시에만 `GoalChanged`에 이전·새 목표, 변경 사유와 구간 증거를 기록합니다. 변경된 목표는 다음 Tick부터 비축량·지출·호가 규칙에 반영됩니다. 매 검토 시 구간 성과를 초기화하고 현재 기준 자산을 저장합니다. 직업은 바꾸지 않습니다.

## 관찰·저장·검증

Inspector는 현재 목표·마지막 검토/변경 Tick, 예약 현금·재고와 진행 중 제안을 보여줍니다. 타임라인은 Proposals/Cooperation/Goals 필터를 지원합니다. CLI 요약·CSV와 실험 보고서에는 `negotiations`, `negotiated_trades`, `cooperations`, `goal_changes`가 들어갑니다. 실험 비교에는 완료 협상·협력·목표 변경의 평균도 포함합니다.

포맷 5 스냅샷은 진행 중 제안, 단조 증가하는 제안 ID, 예약 자산, 목표 성과를 저장합니다. 복원 시 역할·기한·한도·정확한 예약 합계·목표 검토 경계·누적 지표를 검사합니다. JSONL/SQLite Replay는 새 이벤트도 모두 재생성해 비교합니다. `inspect --agent`는 제안·체결·협력 양쪽 참여자를 찾습니다. 이전 엔진의 저장 파일은 자동 마이그레이션하지 않습니다.

LLM에도 동일한 제한된 제안 관찰을 제공하며 새 행동을 구조·역할·기한·자산 검증 후 적용합니다. 잘못된 응답은 기존 규칙 정책으로 대체하고 기록된 결과는 외부 서버 없이 재현합니다. 실제 검증 결과는 [validation.md](validation.md)에 기록합니다.
