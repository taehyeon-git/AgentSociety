# AgentSociety — Rust 기반 자율 멀티 에이전트 사회 시뮬레이터 개발

## 0. 역할과 최종 목표

당신은 Rust 시스템 프로그래밍, 멀티 에이전트 시스템(MAS), 에이전트 기반 모델링(ABM), LLM 에이전트, 경제 시뮬레이션, 데스크톱 애플리케이션 개발 경험이 풍부한 시니어 소프트웨어 엔지니어입니다.

**AgentSociety**라는 이름의 Rust 기반 멀티 에이전트 사회·경제 시뮬레이터를 실제로 설계하고 구현해 주세요.

이 프로젝트는 단순한 LLM 챗봇이나 여러 AI가 대화하는 데모가 아닙니다.

각 에이전트가 고유한 목표, 자원, 직업, 기억, 사회관계, 의사결정 정책을 가지고 하나의 가상 세계에서 자율적으로 행동하는 시스템입니다.

에이전트는 생산, 소비, 거래, 협상, 협력, 경쟁을 수행하며 이러한 행동의 누적으로 시장 가격, 자산 분포, 사회관계, 경제 지표가 변화해야 합니다.

사용자는 시뮬레이션을 실행하고 개별 에이전트의 행동과 전체 사회의 변화를 실시간으로 관찰할 수 있어야 합니다.

최종적으로 다음 조건을 만족해야 합니다.

1. 핵심 시스템은 Rust로 구현합니다.
2. Python을 사용하지 않습니다.
3. LLM 없이도 독립적으로 실행됩니다.
4. 선택적으로 외부 LLM API와 Ollama를 연동할 수 있습니다.
5. 수백 개 이상의 에이전트를 시뮬레이션할 수 있는 구조를 갖춥니다.
6. 에이전트의 상태와 행동에 따라 경제·사회 시스템이 실제로 변화합니다.
7. 사용자가 시뮬레이션을 실시간으로 관찰하고 제어할 수 있습니다.
8. 시뮬레이션의 저장, 복원, 통계 분석, 결정론적 재현을 지원합니다.
9. 단순 예제가 아니라 실제 실행 가능한 프로젝트로 완성합니다.

단, 모든 기능을 한 번에 구현하려고 하지 말고, **작동하는 MVP를 먼저 완성한 다음 단계적으로 확장**해 주세요.

# 1. 기술 스택

기본적으로 다음 기술을 사용합니다.

| 영역 | 기술 |
|---|---|
| 언어 | Rust Stable |
| 프로젝트 관리 | Cargo Workspace |
| ECS | bevy_ecs |
| 비동기 처리 | Tokio |
| LLM 연동 | Rig 또는 자체 HTTP 어댑터 |
| HTTP 통신 | Reqwest |
| 데이터 직렬화 | Serde / serde_json |
| 그래프 자료구조 | petgraph |
| 난수 생성 | rand / rand_chacha |
| 저장소 | SQLite, 필요 시 JSONL 이벤트 로그 |
| 데스크톱 GUI | egui / eframe |
| 그래프 시각화 | egui_plot |
| CLI | clap |
| 오류 처리 | thiserror / anyhow |
| 로깅 | tracing |
| 테스트 | Rust 기본 테스트 프레임워크 |

위 라이브러리의 버전과 API 호환성을 확인하고 서로 호환되는 안정 버전을 선택하세요.

가능하면 UI까지 Rust로 구현합니다.

초기에는 CLI 기반 MVP를 완성한 후 GUI를 추가하세요. 첫 단계부터 복잡한 그래픽 엔진에 종속되지 않도록 설계해야 합니다.

# 2. 전체 시스템 아키텍처

다음 모듈을 중심으로 Cargo Workspace를 구성해 주세요.

## 2.1 World Engine

가상 세계의 상태와 시간 진행을 관리합니다.

담당 기능:

- 시뮬레이션 시간 및 Tick 관리
- 가상 도시와 지역 관리
- 생산 가능한 자원 및 환경 설정
- 에이전트의 위치와 상태
- 전체 세계 상태 저장
- 시뮬레이션 일시정지 및 재개
- 시뮬레이션 속도 제어

세계는 Tick 기반 이산 시간 모델을 사용합니다.

같은 초기 상태, 동일한 난수 시드, 동일한 외부 의사결정 기록이 주어지면 재현 실행의 결과가 일치하도록 설계하세요.

## 2.2 Agent Engine

각 에이전트는 독립적인 상태를 가지고 행동합니다.

기본 데이터 모델:

- AgentId
- Name
- Age
- Occupation
- Personality
- Goals
- Needs
- Inventory
- Wallet
- Skills
- Relationships
- Memory
- CurrentAction
- DecisionPolicy

초기 직업은 다음 4개입니다.

- Farmer: 식량 생산
- Producer: 원자재 기반 상품 생산
- Merchant: 자원 매입 및 판매
- Consumer: 자원 소비 및 구매

각 에이전트의 목표는 서로 다를 수 있어야 합니다.

예시:

- 자산 극대화
- 필수 자원 확보
- 안정적인 생활 유지
- 거래 이익 극대화
- 특정 에이전트와 협력

목표에 따라 서로 다른 행동을 선택해야 합니다.

에이전트의 행동은 선언적인 Action 또는 Intent 타입으로 표현하세요.

예시 행동:

- Produce
- Consume
- Buy
- Sell
- Move
- Negotiate
- Cooperate
- Rest
- Wait

행동 선택과 상태 변경을 분리하세요.

에이전트의 의사결정 결과는 검증된 후 Simulation Engine에서 적용되어야 합니다.

## 2.3 Economy Engine

가상 경제 시스템을 구현합니다.

최소 지원 자원:

- Food
- Wood
- Metal
- Goods

기본 기능:

1. 자원 생산
2. 자원 소비
3. 재고 관리
4. 시장 주문 생성
5. 매수·매도 주문 매칭
6. 거래 체결
7. 시장 가격 갱신
8. 자산 및 소득 계산
9. 수요·공급 통계
10. 부의 분포 분석

초기 시장은 중앙 집중형 주문장으로 구현합니다.

매수·매도 호가, 수량, 주문 시간 등을 이용해 명확하고 재현 가능한 매칭 규칙을 설계하세요.

경제 시스템에서는 다음 불변조건이 중요합니다.

- 거래 시 화폐 이동과 자원 이동은 원자적으로 처리합니다.
- 거래는 양쪽 에이전트의 잔액과 재고가 충분할 때만 성립합니다.
- 잔액과 재고가 음수가 되어서는 안 됩니다.
- 생산·소비·시장 거래에서 발생하는 자원 변화를 구분합니다.
- 신규 화폐 발행이 없다면 거래만으로 전체 화폐량이 변하지 않아야 합니다.
- 가격 계산에서 0으로 나누기, 오버플로, NaN 등의 문제가 발생하지 않도록 합니다.
- 화폐는 가능하면 부동소수점 대신 정수 최소 단위로 표현합니다.

초기에는 복잡한 현실 경제를 그대로 복제하지 않아도 됩니다.

다만 시장 규칙과 자산 변화가 논리적으로 일관되어야 합니다.

## 2.4 Social Engine

에이전트 사이의 사회관계를 모델링합니다.

각 에이전트는 다른 에이전트에 대한 관계 정보를 가집니다.

관계 속성:

- Trust
- Familiarity
- CooperationScore
- InteractionCount

에이전트는 거래 성공, 거래 실패, 협력, 협상 등의 결과에 따라 관계 점수를 변경합니다.

예를 들어 반복적으로 거래에 성공한 상대방에 대한 신뢰도가 상승하거나, 협상 실패 후 관계가 악화될 수 있습니다.

이러한 관계 점수가 이후 거래·협력·상대방 선택에 영향을 미치도록 하세요.

사회관계는 그래프 구조로 저장하고 시각화할 수 있도록 설계합니다.

처음에는 단순한 가중치 그래프로 구현하고, 이후 커뮤니티 형성이나 네트워크 분석으로 확장할 수 있도록 합니다.

## 2.5 Cognition Engine

에이전트 의사결정 시스템입니다.

이 프로젝트의 핵심 기능 중 하나입니다.

의사결정 엔진은 다음 세 가지 정책을 교체 가능하도록 설계하세요.

**A. RuleBasedPolicy**

LLM 없이 실행되는 기본 정책입니다.

에이전트의 상태, 목표, 재고, 시장 가격 등에 따라 행동을 선택합니다.

예시:

- 식량 부족 시 구매 시도
- 생산에 필요한 원자재 부족 시 구매
- 잉여 생산물이 있을 때 판매
- 자산이 부족하면 수익성 높은 행동 우선
- 신뢰도 높은 거래 상대 선호

**B. LlmPolicy**

LLM을 사용해 복잡한 행동을 결정합니다.

LLM에는 현재 에이전트 상태, 관련 세계 정보, 제한된 기억, 가능한 행동 목록을 전달합니다.

모델 응답은 자유 형식 문자열이 아니라 구조화된 JSON으로 받습니다.

예시 필드:

- action
- target_agent_id
- resource
- quantity
- offered_price
- reasoning_summary

LLM이 반환한 행동은 반드시 검증한 후 실행해야 합니다.

유효하지 않은 행동을 제시하면 재시도하거나 RuleBasedPolicy로 대체합니다.

**C. HybridPolicy**

RuleBasedPolicy와 LlmPolicy를 결합합니다.

단순 행동은 규칙 기반으로 처리하고 복잡한 판단만 LLM을 사용합니다.

LLM 호출 조건 예시:

- 새로운 거래 전략이 필요한 경우
- 협상할 상대를 선택하는 경우
- 자산이 지속적으로 감소하는 경우
- 기존 행동 정책의 성과가 낮아진 경우
- 장기 목표를 재설정하는 경우

LLM 호출 빈도와 동시 실행 수를 제한합니다.

에이전트 수와 Tick 수에 비례해 LLM 호출 비용이 폭증하지 않도록 설계하세요.

LLM 응답을 기다리는 동안 전체 시뮬레이션이 무기한 정지하지 않도록 타임아웃과 결과 적용 시점을 명확히 정의합니다.

LLM이 반환한 행동은 이벤트 로그에 기록하여 재현 실행에서 다시 호출하지 않고 사용할 수 있어야 합니다.

## 2.6 Memory Engine

각 에이전트는 과거 사건을 기억해야 합니다.

메모리 타입:

- EpisodicMemory: 특정 경험과 사건
- SocialMemory: 다른 에이전트와의 상호작용
- EconomicMemory: 거래 가격과 수익 기록
- GoalMemory: 목표와 전략 변경 이력

초기에는 구조화된 메모리 저장소로 구현하세요.

각 기록에는 다음 정보가 포함됩니다.

- MemoryId
- AgentId
- Timestamp / Tick
- EventType
- Content
- Importance
- RelatedAgentIds

메모리 검색은 최근성, 중요도, 현재 상황과의 관련도를 기준으로 처리합니다.

모든 과거 사건을 매번 LLM에 전달하지 마세요.

관련 기억만 선택적으로 요약하거나 추출하는 구조가 필요합니다.

초기에는 벡터 데이터베이스를 사용하지 않아도 됩니다. 구조화된 메모리 검색을 먼저 완성합니다.

## 2.7 Simulation Engine

전체 시스템을 통합하는 실행 엔진입니다.

기본 Tick 순서:

1. 세계 상태 확인
2. 각 에이전트의 관찰 데이터 생성
3. 에이전트별 행동 결정
4. 행동 검증
5. 생산·이동 등 개별 행동 처리
6. 시장 주문 매칭과 거래 정산
7. 소비 및 욕구 상태 갱신
8. 사회관계·기억 갱신
9. 이벤트 저장
10. 통계 계산
11. Tick 종료

위 순서는 권장안입니다. 주문 체결과 행동 충돌 등을 고려해 더 일관된 순서가 필요하면 변경하고 이유를 문서화하세요.

동일한 자원을 여러 행동이 동시에 사용하는 문제를 방지해야 합니다.

초기에는 결정론적 단일 스레드 상태 변경 방식을 사용해도 됩니다.

LLM 요청이나 UI 처리에는 비동기 처리를 활용하되, 세계 상태 변경을 무분별하게 병렬화하지 마세요.

결정론적 실행을 확보한 뒤 성능을 개선하세요.

# 3. GUI 및 시각화

Rust 기반 egui/eframe으로 시뮬레이션 대시보드를 구현합니다.

최소한 다음 화면이 필요합니다.

**World View**

- 전체 에이전트 표시
- 에이전트 위치와 상태
- 직업별 구분
- 에이전트 선택
- 현재 Tick 표시
- 실행, 일시정지, 재시작
- 시뮬레이션 속도 조절

**Agent Inspector**

특정 에이전트를 선택했을 때 다음 정보를 표시합니다.

- 이름과 직업
- 현재 목표
- 자산
- 보유 자원
- 현재 행동
- 최근 행동 이력
- 주요 사회관계
- 최근 기억
- AI 의사결정 결과

**Economy Dashboard**

- 전체 거래량
- 자원별 시장 가격
- 평균 자산
- 부의 불평등 지수(Gini)
- 자원 생산량과 소비량
- Tick별 경제 지표 그래프

**Event Timeline**

- 생산
- 거래 성립
- 협상
- 사회관계 변경
- 주요 목표 변경
- 에이전트별 행동 이력

상세 이벤트를 시간순으로 조회할 수 있어야 합니다.

초기 GUI는 복잡한 3D 세계가 아니어도 됩니다.

2D 지도, 에이전트 마커, 통계 패널 중심으로 구현하세요.

실제로 데이터를 확인하고 조작할 수 있는 UI를 우선합니다.

# 4. 이벤트 기록 및 재현

모든 중요한 상태 변경을 추적할 수 있어야 합니다.

예시 이벤트:

- AgentCreated
- ResourceProduced
- ResourceConsumed
- OrderPlaced
- TradeExecuted
- RelationshipUpdated
- GoalChanged
- DecisionRecorded
- TickCompleted

구조화된 이벤트를 저장하고 조회할 수 있도록 합니다.

시뮬레이션의 재현성을 위해 다음을 기록합니다.

- 초기 시드
- 시뮬레이션 설정
- 초기 세계 상태
- 이벤트 순서
- 외부 LLM 의사결정 결과
- 필요한 외부 입력
- 버전 정보

Replay 모드에서는 저장된 이벤트를 순서대로 재적용하거나 기록된 의사결정을 재사용하여 실행 상태를 재현합니다.

LLM의 비결정적 출력이나 비동기 작업 완료 순서가 재현성을 깨뜨리지 않도록 설계해야 합니다.

초기에는 JSONL 이벤트 로그와 상태 스냅샷으로 시작할 수 있습니다.

이후 SQLite 영속화 및 체크포인트 기능을 추가하세요.

# 5. 성능 및 실행 요구사항

개발 환경은 일반적인 개인용 컴퓨터나 노트북을 고려합니다.

초기 목표:

- 에이전트 10개: 기능 검증
- 에이전트 100개: 기본 동작 및 GUI 검증
- 에이전트 1,000개: 규칙 기반 시뮬레이션 성능 평가

1,000개 에이전트에서 모든 기능이 처음부터 고성능으로 동작해야 한다는 의미는 아닙니다.

측정 결과를 토대로 병목을 찾고 최적화하세요.

성능 평가 항목:

- Tick 처리 시간
- 에이전트 수에 따른 처리량
- 메모리 사용량
- 시장 주문 처리 시간
- 이벤트 기록 오버헤드
- LLM 사용 시 추가 지연과 비용

LLM을 사용하지 않는 모드에서는 네트워크 연결 없이 동작해야 합니다.

# 6. 테스트 요구사항

핵심 엔진에는 반드시 자동화 테스트를 작성하세요.

**경제 시스템 테스트**

- 재고가 없는 에이전트는 판매할 수 없음
- 잔액이 부족한 에이전트는 구매할 수 없음
- 거래 전후 자원과 화폐 보존 확인
- 주문 부분 체결 및 미체결 처리
- 동일한 자원의 중복 사용 방지

**시뮬레이션 테스트**

- 동일 시드와 동일 입력에서 동일 결과
- 에이전트 0명, 1명, 다수인 경우 처리
- 에이전트 100명의 연속 실행
- 1,000 Tick 이상 실행
- 저장 후 복원한 상태의 일관성
- 기록 기반 Replay 결과 검증

**의사결정 테스트**

- 유효한 행동 선택
- 잘못된 LLM JSON 응답
- 허용되지 않은 행동
- LLM 타임아웃
- 규칙 기반 정책으로 대체
- 호출 횟수 제한

테스트 통과 여부를 실제 실행 결과로 확인하세요.

# 8. 단계별 개발 계획

다음 순서로 구현합니다.

## Phase 1 — 실행 가능한 기본 MVP

가장 먼저 이 단계를 완성하세요.

구현 범위:

- Cargo Workspace 생성
- 기본 World 구조
- Agent 구조
- 4개 직업 구현
- 기본 자원 및 경제 규칙
- RuleBasedPolicy
- Tick 기반 Simulation Engine
- CLI 명령어
- 시드 기반 난수 생성
- 기본 통계 출력
- 단위 테스트

완료 기준:

- 에이전트 100명을 생성할 수 있음
- 1,000 Tick을 실행할 수 있음
- 생산, 소비, 거래가 실제 발생함
- 에이전트별 자산 및 재고가 변화함
- 시장 통계를 출력함
- 불변조건 테스트 통과
- 동일 시드로 실행한 결과가 재현됨

실행 예시:

`cargo run -p agentsociety-cli -- --agents 100 --ticks 1000 --seed 42`

명령어 이름은 실제 Cargo 패키지 이름과 일치하도록 구현하세요.

## Phase 2 — 시각화 및 사회관계

구현 범위:

- egui/eframe GUI
- 2D World View
- Agent Inspector
- 경제 통계 그래프
- Event Timeline
- 에이전트 관계 그래프
- 시뮬레이션 시작·중지·속도 제어

완료 기준:

사용자가 GUI를 실행하고 에이전트의 행동과 사회·경제 변화를 실시간으로 관찰할 수 있어야 합니다.

## Phase 3 — Memory 및 LLM 통합

구현 범위:

- 구조화된 에이전트 기억
- RuleBasedPolicy / LlmPolicy / HybridPolicy
- Ollama 연동
- OpenAI 호환 API 어댑터
- 행동 JSON 검증
- LLM 호출 제한
- 타임아웃 및 실패 처리
- 의사결정 기록

완료 기준:

기본 규칙 기반 모드와 LLM 모드를 전환할 수 있어야 합니다.

LLM 서버가 작동하지 않아도 기본 시뮬레이션은 계속 실행되어야 합니다.

## Phase 4 — 재현 및 실험 시스템

구현 범위:

- 상태 스냅샷
- 이벤트 기반 Replay
- SQLite 저장
- 실행 설정 저장
- 여러 시드의 실험 비교
- 시뮬레이션 결과 내보내기
- 성능 벤치마크

완료 기준:

동일 조건의 실험을 반복하고 결과를 비교할 수 있어야 합니다.

저장된 실행을 복원하고 개별 에이전트의 과거 행동을 확인할 수 있어야 합니다.

## Phase 5 — 고급 멀티 에이전트 기능

기본 기능이 안정화된 이후 진행합니다.

확장 후보:

- 에이전트 간 협상 프로토콜
- 에이전트의 장기 목표 설정
- 집단 형성 및 협력
- 에이전트 전략의 적응
- 시장 환경 변화
- 경제 위기 시나리오
- 정책 변화에 따른 행동 분석
- 다양한 의사결정 정책의 비교 실험

고급 기능은 새로운 모듈을 추가하는 방식으로 확장할 수 있도록 설계하세요.

# 9. 개발 원칙

다음 규칙을 지켜 주세요.

1. 설계 문서만 작성하지 말고 실제 Rust 코드를 구현하세요.
2. 기존 프로젝트가 있다면 먼저 파일 구조를 확인하고 관련 없는 코드를 변경하지 마세요.
3. 각 Phase를 실행 가능한 상태로 완성하세요.
4. Phase가 끝날 때마다 빌드와 테스트를 수행하세요.
5. 컴파일 오류를 남긴 채 완료되었다고 보고하지 마세요.
6. 임시 하드코딩이나 더미 데이터로 핵심 기능을 구현한 것처럼 처리하지 마세요.
7. 실제 동작하지 않는 기능은 미구현 상태로 명확히 표시하세요.
8. 오류를 숨기지 말고 명시적으로 처리하세요.
9. 핵심 엔진은 GUI 및 특정 LLM 제공자와 독립적으로 동작해야 합니다.
10. 코드에는 필요한 주석을 작성하고 공개 API에는 Rust 문서 주석을 작성하세요.
11. 기능을 추가할 때 필요한 단위 테스트 및 통합 테스트도 함께 작성하세요.
12. 구현 후 `cargo fmt`, `cargo clippy`, `cargo test`를 실행하세요.
13. 성능 최적화는 실제 측정 결과를 토대로 진행하세요.
14. 모든 외부 API 키는 환경변수로 관리하고 저장소에 포함하지 마세요.
15. 프로젝트 진행 상황과 미완료 작업은 문서로 관리하세요.

# 11. 지금 바로 수행할 작업

우선 현재 작업 디렉터리와 사용 가능한 Rust 개발 환경을 확인하세요.

이후 아래 순서로 작업을 진행합니다.

**Step 1.** 전체 시스템의 구현 가능한 아키텍처를 설계합니다.

**Step 5.** 경제 불변조건, 결정론, 연속 실행 테스트를 작성하고 검증합니다.

**Step 6.** 빌드·테스트 결과, 구현된 기능, 미구현 기능, 다음 개발 순서를 정리합니다.

이번 작업에서 **Phase 1이 우선순위**입니다.

Phase 1의 핵심 기능이 완성되지 않았다면 단순한 UI 화면이나 과도한 부가기능을 먼저 구현하지 마세요.

Phase 1을 완성하고 테스트를 통과한 경우에만 Phase 2로 진행하세요. 토큰·시간·실행 환경 제약으로 중단해야 한다면 컴파일 가능한 상태를 유지하고 현재 진행 상황을 문서에 남기세요.

모호한 세부사항은 프로젝트 목표에 맞는 합리적인 기본값을 선택하고 기록하세요. 불필요한 확인 질문 없이 작업을 진행하세요.

최종 목표는 **LLM과 규칙 기반 에이전트가 하나의 가상 사회에서 자율적으로 행동하며, 사회·경제적 현상이 나타나는 과정을 관찰·분석·재현할 수 있는 Rust 기반 AgentSociety**를 완성하는 것입니다.
